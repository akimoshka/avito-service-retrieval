# Avito Service Retrieval

Решение тестового задания по генерации кандидатов для поиска услуг Avito.

## Задача

Необходимо для каждого поискового запроса из `benchmark_queries.parquet` выбрать до 50 наиболее релевантных объявлений из `benchmark_items.parquet`.

Итоговая метрика вычисляется как средний Recall@50 по запросам.

Поскольку порядок объявлений внутри Top-50 не влияет на метрику, задача рассматривается как candidate generation, а не как задача финального ranking.

Данные не добавляются в Git-репозиторий и должны быть расположены локально в `data/raw/`.

---

## Анализ данных

Train содержит 497 673 положительных взаимодействий query–item.

Benchmark:
- 2 452 поисковых запроса
- 189 212 объявлений

В ходе EDA были получены следующие наблюдения.

### - Пересечение запросов

В train содержится 74 529 уникальных текстов запросов. Около **37% benchmark-запросов** имеют точное текстовое совпадение с запросами из train.

Это показывает, что исторические взаимодействия потенциально могут использоваться как дополнительный retrieval-сигнал, однако решение должно также корректно работать для ранее невидимых запросов.

### - Количество релевантных объявлений

Для большинства запросов количество положительных объявлений невелико:
- 60.58% запросов имеют одно релевантное объявление;
- 74.81% - не более двух;
- 87.54% - не более пяти.

Поэтому попадание релевантного объявления в Top-50 особенно важно для итогового Recall.

### - Категория

Практически все положительные взаимодействия относятся к `item_category_id = 114`. При этом около 99% benchmark corpus также принадлежит этой категории, поэтому жёсткая фильтрация по категории практически не уменьшает пространство поиска и не использовалась в финальном решении.

### - Локация

Для примерно **83.1%** положительных взаимодействий выполняется `search_location_id == item_location_id`. Таким образом, географическое совпадение является сильным сигналом релевантности. При этом location не используется как жёсткий фильтр, поскольку около 17% положительных взаимодействий происходят между различными локациями.

## Validation

Для локальной оценки был сформирован validation split по уникальным текстам `search_query`. Случайно выбираются 2 452 уникальных поисковых запроса, после чего все взаимодействия с этими текстами полностью исключаются из retrieval train.

Таким образом, validation моделирует достаточно строгий сценарий работы с unseen queries. Для каждого query context формируется множество релевантных `item_id`, после чего качество оценивается с помощью среднего `Recall@50`.

Validation corpus состоит из benchmark items и положительных объявлений validation. Все relevant items присутствуют в validation corpus.

> Такой split является более строгим, чем реальный benchmark: часть benchmark-запросов встречается в train. Поэтому локальный Recall используется прежде всего для сравнения retrieval-подходов, а не как точная оценка leaderboard score.

---

## Lexical retrieval

В качестве базового candidate generator используется **TF-IDF (Term Frequency - Inverse Document Frequency)**.

TF-IDF преобразует тексты в разреженные числовые векторы, увеличивая вес терминов, характерных для конкретного документа, и уменьшая влияние слов, часто встречающихся во всей коллекции.

Релевантность объявления запросу определяется через **cosine similarity** между TF-IDF вектором `search_query` и TF-IDF вектором текста объявления. Чем больше у запроса и объявления общих информативных слов и словосочетаний, тем выше lexical similarity.

Используются как отдельные слова, так и пары соседних слов (`ngram_range=(1, 2)`), что позволяет учитывать выражения вроде `ремонт холодильника`, `установка кондиционера` и другие характерные для поиска услуг словосочетания.

Для каждого объявления формируется текстовое представление из доступных текстовых признаков.

Были протестированы следующие варианты:

| Эксперимент | Представление | Recall@50 |
|---|---|---:|
| B1 | title | 0.1880 |
| B2 | title + params | 0.1882 |
| B3 | title + params + description | **0.2328** |
| B4 | title + description | 0.2131 |
| B5 | Character TF-IDF | 0.2240 |

Лучшим чисто текстовым вариантом оказался:

`item_title_raw + item_infm_params_text + item_description_raw`

Для поискового запроса используется `search_query`.

### TF-IDF параметры

```python
TfidfVectorizer(
    lowercase=True,
    ngram_range=(1, 2),
    min_df=2,
    max_df=0.95,
    sublinear_tf=True,
    dtype=np.float32,
)
```

Retrieval выполняется батчами и использует sparse matrix multiplication, что позволяет избежать построения полной dense query-item матрицы.

## Location-aware retrieval

Анализ данных показал сильную зависимость релевантности от географического положения. Поэтому к lexical similarity был добавлен мягкий bonus за совпадение локации:


```text
score(q, i) = cosine(TFIDF(q), TFIDF(i)) + α · I(location_q = location_i)
```

где:
- `cosine(TFIDF(q), TFIDF(i))` - cosine similarity между TF-IDF-векторами запроса и объявления
- `I(location_q = location_i)` - индикатор совпадения локации
- `α` - коэффициент location boost

Проверенные значения:

| Location boost α | Recall@50 |
|---:|---:|
| 0.05 | 0.4183 |
| 0.10 | 0.5087 |
| **0.20** | **0.5392** |

Лучший среди проверенных вариантов з `α = 0.20`.

По сравнению с чистым lexical baseline:

```text
TF-IDF                       0.2328
TF-IDF + location            0.5392
```

Учёт географического контекста дал наиболее существенный прирост качества.

## Финальный подход

Финальный candidate generator состоит из следующих этапов:

1. Объединение `item_title_raw`, `item_infm_params_text` и `item_description_raw`
2. Построение Word TF-IDF с unigram + bigram признаками
3. Вычисление lexical similarity между `search_query` и benchmark items
4. Выбор расширенного набора до 500 lexical candidates.
5. Добавление `0.20` к score объявления при совпадении `search_location_id` и `item_location_id`
6. Выбор итоговых Top-50 объявлений
7. Для редких запросов с недостаточным количеством lexical candidates используется fallback: сначала объявления из той же локации, затем объявления из общего benchmark corpus

Итоговый локальный результат: **Recall@50 = 0.5392**

## Запуск

### 1. Установка зависимостей

```bash
pip install -r requirements.txt
```

### 2. Подготовка данных

Исходные файлы должны находиться в:

```text
data/raw/train.parquet
data/raw/benchmark_queries.parquet
data/raw/benchmark_items.parquet
```

### 3. Генерация submission

Из корня проекта:

```bash
python scripts/generate_submission.py
```

Скрипт:

- загружает benchmark queries и items
- строит TF-IDF представление
- выполняет retrieval
- применяет location boost
- выбирает Top-50
- выполняет проверки результата
- сохраняет submission

Результат:

```text
outputs/answer.csv
```

Формат:

```csv
query_id,answer
70DfDUpwjxB4lzFd,6042fecdd7753112 f4e8903d7689e222 603623b4bd9e8f6c ...
JTrdTaZJvSiLPkXj,cbeccbecb1fb8d86 5e62c7a98f91a124 ...
```

Каждая строка соответствует одному `query_id`. Для каждого запроса генерируется до 50 различных `item_id`, записанных в одной строке через пробел.

`query_id` и `item_id` сохраняются как строки без изменения регистра.

---

## Проверки submission

Перед сохранением результата автоматически проверяется:

- наличие ровно двух колонок: `query_id` и `answer`
- наличие всех 2 452 benchmark queries
- ровно одна строка для каждого `query_id`
- корректная длина `query_id` — 16 символов
- не более 50 `item_id` на запрос
- корректный формат `item_id` — 16 символов `0-9a-f`
- отсутствие неизвестных `item_id`
- отсутствие повторяющихся `item_id` внутри ответа одного запроса
- отсутствие запросов без кандидатов

Финальный submission содержит:

```text
benchmark queries:             2 452
submission rows:               2 452
unique query_id:               2 452
missing queries:                   0
candidates per query:             50
unknown item_id:                   0
duplicate item_id:                 0
invalid item_id format:            0
invalid query_id length:           0
```
